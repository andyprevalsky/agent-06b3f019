BENCHMARK PARENT AGENT INSTRUCTIONS · FORMAT v8

This file owns the benchmark card. Every shared display rule (12-hour America/Los_Angeles clocks, one status emoji, current-assignment tokens and rolling 15-minute tokens/min, LIFE at the far right, freshness, colors, no null fields or legends) is in `.claude/shared/report-display-format.md`.

Render and publish (mandatory)
- The card is generated, never hand-written: every launch prints its exact command; render only with `scripts/run-bench scorecard <run-dir> --html <run-dir>/scorecard.html` and publish that file unchanged through `boxes-inline-visualizations` (`dvb-onbox visuals publish --file <run-dir>/scorecard.html --title "<label> scorecard"`), returning its standalone link. No prose before or after it.
- A hand-written, edited or re-typed card is non-compliant; `scripts/run-bench scorecard --validate <card.html>` rejects it.
- Off boxes.dev, or when HTML is unavailable, post `scripts/run-bench scorecard <run-dir> --text` in one diff fence and state that limitation.
- Pass active sub-agent rows with `--agents <rows.json>` and owner-assigned issues with `--issues <issues.json>`; every other value comes from recorded run artifacts and the git-common experiments ledger, so fix a wrong or missing value in its producer or artifact, never in the card.
- Never show stale data: every `--agents`/`--issues` row carries `observed_at`, rebuilt from the live run, worker results and merged HEAD at render time; the renderer refuses the card (exit 1, no HTML) when a row lacks it, is older than 15 minutes or predates the run's end, so re-observe and re-render, never backdate or omit it.
- This is the standard card for every CLI benchmark route (cloud, local, eval, campaign, sharded, production-only), its progress updates and its final report.
- Publish the card on agent start/completion, every fixed 15-minute checkpoint, and benchmark-state changes; events never postpone or reset the checkpoint or run clock, and publishing never pauses workers or cancels the experiment.
- Never pause workers to edit or discuss their scorecard.

Card layout
- Generic cards use the layout below; all /descend cards use the full-suite
  cake/curve and lifecycle-display exception specified later in this contract.
- Top to bottom: Experiment # and state; KPI tiles (pass %, infra % with the stop threshold, QUEUED/IN_PROGRESS/COMPLETED progress, elapsed, execution window); the outcome bar with PASS, HARNESS FAILURE and INFRA FAILURE always shown; failure causes; timing/cost/cache/LLM coverage; the lifecycle checklist; LAST 3 EXPERIMENTS; active sub-agents; ISSUES / NEXT ACTION.
- At the top, **Since last benchmark ended** shows the latest actual benchmark's label and elapsed time from its producer terminal timestamp; diagnostics, cleanup and card refreshes never reset it; a live run shows RUNNING and a missing end END UNRECORDED.
- Active sub-agent rows and their placement follow report-display-format.md (Agent rows, Placement).
- ISSUES / NEXT ACTION stays concise: each concrete issue with its owner and action; never reintroduce removed global sections.
- Report deploy state separately from task verdicts.
- Evidence identifies this concrete slice/group and its durable viewer, keeping individual run/agent references; never cite ephemeral localhost or tunnel viewers.

Experiments
- The first card row names the current **Experiment #** and state; launch paths (fleet, campaign, sharded operator) append one immutable line per actual launch and end to `<git-common>/cloudbench-experiments.jsonl`, from which the CLI computes the Experiment #, Experiments/day = verified launches / elapsed goal days, and LAST 3 EXPERIMENTS.
- Experiments/day counts distinct actually launched original experiments since the preserved original goal start, excluding local diagnostics, tests and prepared drafts; backfilled or partial history is labelled a lower bound with its verified launch count and elapsed days; never equate the sequence number with the launch count or type these values by hand.
- Preserve the slice's original `triggered_at` (with timezone), requested names and count, run/group IDs, full source checkpoint, original timeouts and every attempt; retries, later uploads and recovery never reset those clocks.
- A prepared run is explicitly **NOT LAUNCHED**; any queued count is labelled `planned`, never dispatched work or an actual experiment.
- LAST 3 EXPERIMENTS shows only the latest three actual qualification experiments, newest first (full history stays internal and experiments/day uses every verified launch); it replaces LAST SLICE TRIGGERED, WHY NO NEW SLICE, BENCHMARK PROGRESS, ACTIVE RUN and the standalone cost/cache/LLM block.
- Each is a compact row with a mini outcome bar (experiment, state, trigger, producer end, total elapsed) plus aligned subrows for QUEUED/IN_PROGRESS/COMPLETED counts, PASS/HARNESS FAILURE/INFRA FAILURE, genuine agent failures, unknown outcomes, cost, cache, LLM latency and lifecycle coverage.
- Ends come from the actual producer terminal artifact, never an observer capture or export completion; a live experiment reads RUNNING with ELAPSED from its original trigger, and an unknown historical end reads END UNRECORDED with duration UNMEASURED.
- Once a descent goal has more than three completed iterations, pass its count
  to `scripts/run-bench scorecard` with `--iterations N` and show SUCCESS RATE
  OVER TIME above the history rows. Outside descent, use more than three
  launched experiments as the threshold. Plot task PASS divided by scored tasks for
  every experiment in goal order. Leave experiments with no scored tasks as
  gaps, and draw a still-running experiment's point hollow. The text fallback
  lists the same percentages and gaps.

Progress and outcomes
- The headline QUEUED, IN_PROGRESS and COMPLETED counts are scheduled logical members (not child agents or retries) summing to the requested total: queued has not started; in progress spans startup, execution and evaluation, and retrying members stay there; COMPLETED is a recorded terminal outcome, not a pass, including infrastructure, cancelled or skipped outcomes.
- Directly below, PASS, HARNESS FAILURE and INFRA FAILURE appear on every card, with genuine AGENT FAILURE, cancelled, skipped, unscored and unknown outcomes shown separately rather than folded into PASS/FAIL; there is no scheduled PENDING result row.
- HARNESS FAILURE needs evidence of an orchestration/runner failure; never relabel a genuine task/agent failure, read a missing classification as zero, or sum overlapping categories.
- Task PASS/FAIL uses all scored verdicts (PASS + task FAIL) as its denominator, excluding infra, cancellation, skip and pending; INFRA is infra failures / ALL terminal attempts including retained retries, numerator and denominator printed; recovered tool/model errors alone are not infra failures, and infra is never hidden under task FAIL.
- Use NO SCORED TASKS or NO TERMINAL ATTEMPTS instead of 0/0 rates, preserving actual zero counts; unknown classifications stay unknown until evidence classifies them.
- The infra stop is a small note on the original scheduled total, `Stop at <threshold>/<original scheduled> unique infra-failed jobs (5%)` (for 600 jobs, 30/600), never a headline metric; an earlier wrong 1/1 stop is an erroneous early abort, not a valid breach or a retroactive pass; machine admission and qualification counts go in supporting details.

Timing, cost and lifecycle
- Execution time starts at actual task execution, not provisioning or controller start: queued execution reads NOT STARTED with the oldest wait reported separately; active execution shows min/max elapsed across executing members; completed p50/p95 uses only tasks with measured execution, omitting unmeasured quantiles with a coverage note.
- Show full elapsed since trigger and since the goal started, blocked windows with reasons, per-stage p50/p95 and all attempt/retry counts; parallel stage timings overlap, so never sum their medians as wall time.
- Keep original bounds (including a recorded 10800-second no-new-run delay) in telemetry; a delay that needs action goes in ISSUES / NEXT ACTION with its owner, not a separate last-slice block.
- Metrics stay scoped to each experiment and all its attempts; costs accumulate across every attempt and provider (agents, WMH, infrastructure, Azure, others), separating estimates from billed receipts and naming incomplete coverage.
- Keep DEMO response replay separate from agent and WMH prompt-cache rates, each with its actual hit/look-up or cached-input/all-input denominator; an enabled flag does not prove a hit; report agent and WMH LLM avg/p95/p99 separately.
- PASS/FAIL and the terminal-member COMPLETE count may publish before cleanup, but the final workflow status COMPLETE requires controller exit, published final results and verified release of the exact owned resources; an early outcome ACK, pool return or preservation archive is not full release.

Descent presentation override (explicit user default)
- Descent cards retain every fixed 15-minute checkpoint and original +900-second anchors.
- `--iterations N` (including zero) selects the `/descend` display: up to LAST 10
  actual selected experiments, newest first; generic cards retain LAST 3.
- Put Iterations/Hour prominently at the top: 3600 / seconds between the latest
  consecutive completed producer finishes. While #8 runs use #6 → #7; after #8
  finishes use #7 → #8. Count all intervening work/gaps, never launch rate or
  execution time. Missing/reversed/nonpositive intervals remain UNMEASURED and
  never bridge an intervening missing experiment.
- Each finished history row shows T-<age> since finish (NOW minus original
  producer finish). Running rows show T-RUNNING; unknown/future ends show
  T-UNRECORDED. Browser updates age text only; original timestamps never move.
- Keep sources, grades, costs, lifecycle and explicit history scope unchanged.
  Do not add fake rows. Generic experiments/day may remain secondary. The >3
  descent-iteration threshold for the success graph is unchanged.

Maintain the run (this card is not a stopping point)
- Continuously advance the authorized goal (observe, delegate, diagnose, fix, verify, publish, run the next slice); never return after merely launching a run or sending a card, and end only when the goal is complete or the user stops the work.
- The assigned operational owner polls the exact CLI-printed monitor on CLAUDE.md's background-task cadence, reading controller exit and cleanup receipts on every observation even when the card is stale; campaign `summary.json` and each child's printed monitor handle are distinct.
- Reread missing or stale observations; they never authorize a restart, broader cleanup, a clock reset or cancelling healthy siblings.
- Stop the exact owned run through its normal controller when `scheduled_total > 0` and `20 * infra_failed_jobs >= scheduled_total`: exactly 5% stops (30 of 600; 1/600 and 29/600 continue); never use completed attempts as the denominator or count a retried job twice, and preserve the first breach, original clocks and every physical attempt.
- Iterate through `/descend`: one `/RCA` per failure as it appears, never blocking the next run on a full `/deploy`.
- On boxes.dev, delegate through managed threads (`boxes-delegated-threads`).

### Descent speed change (user clarification)

The compact descent headline is `<rate> iter/h [avg Δ <signed percent> over last 5 runs]`.
Avg Δ uses five consecutive finished recorded experiments (four finish-to-finish
speeds), then takes the arithmetic mean of the three successive changes:
100 * (next_speed / previous_speed - 1). It is neither mean speed nor endpoint
change. Retain failed/cancelled finishes and all inter-experiment work. Skip only
the latest current running experiment; never bridge missing/invalid finishes.
Fewer than five consecutive valid finishes show UNMEASURED with n/5 coverage.
Positive change is green with +, negative red with -, and stationary is 0.0%.
Keep the full Iterations/Hour and finish-to-finish definition in a secondary
line/title; the last ten rows and T- clocks are unchanged.

### All /descend scorecards: full-suite outcomes and measured telemetry

For every descent, render one segmented donut (cake) for the entire persisted
selected task order, using X individual run slots per task: N selected tasks
multiply by X gives the denominator (200 × 2 = 400 slots). Green means that
individual scored run passed; red means that individual scored run failed.
Gray means no scored result in an explicitly unfilled slot; unscored infra or
cancelled attempts may exist. Amber means missing, invalid or unknown receipt/history. One PASS plus one
FAIL contributes one green and one red slot, never a single task-level color.
Missing task rows are unknown, never assumed unrun. Label these historical
outcomes; keep X/X task qualification and final-source acceptance separate.

Use individual PASS slots divided by N × X as the only global time graph,
at original experiment finish
clocks. Missing snapshots are gaps; do not substitute slice percentages or
invent earlier history. Preserve the existing greater-than-three-iterations
threshold and last-ten experiment rows. Remove current-slice outcome bars and
the lifecycle display section for descents; underlying lifecycle, custody,
release checks and unresolved issues remain intact. Generic benchmark displays
retain their existing contract.

Color the descent pass KPI green only above95%, yellow above80%, red otherwise.
Color infra green only below5%, red at or above5%; unknown is amber/unmeasured.
Pass uses scored PASS+FAIL as its denominator; infra uses original scheduled jobs.
Never turn unknown/infra outcomes into a scored PASS or FAIL.

Supply full-scope inputs explicitly:
`--iterations N --global-acceptance acceptance_ledger.json --selected-tasks selected_tasks.json --selected-tasks-sha256 <raw-file-SHA256> --global-runs X --global-history global_history.json`.
The selection uses `descend-selected-tasks-v1` ordered `rows[].name`; acceptance
uses `descend-rolling-acceptance-v1`, matching `task_count` and `k`, unique task
identities and `last_scored` receipts (legacy `last_two_known_scored` is accepted
only for X=2). Each scored receipt must carry its original campaign/job/run,
verdict, source commit, evidence SHA256 and terminal clock. History uses
`descend-global-history-v1`, matching selection hash/count/k and ordered
`snapshots[{experiment_id, finished_at, acceptance_ledger}]`; null ledgers are
gaps. Inputs are read-only and mismatched scope is refused.

Optional `--telemetry telemetry.json --telemetry-membership membership.json --telemetry-sources original-source-packet/ --telemetry-receipt telemetry-receipt.json --telemetry-receipt-sha256 <custodian-receipt-SHA256>` uses `descend-scorecard-telemetry-v1`,
matching `experiment_id`, `scheduled_jobs`, `covered_run_count`, unique
`cost_rows[{job_id, cost_cents, run_json_sha256}]` and unique
`latency_rows[{agent_id, request_id, ttft_seconds, total_seconds, source_sha256}]`.
Durations come from matched native start/productive-chunk/completion observations;
null means missing. Show quantiles with sample/run coverage. Cost is user-metered
agent LLM cost, summed once per original job; it is not total provider expense.
Azure/provider spend, infra and grounding stay UNMETERED without billing evidence.
A partial job-cost input cannot replace a full experiment aggregate. Never infer
latency from a timeout, configuration budget, canary, or unrelated run.

Telemetry membership uses `descend-scorecard-membership-v1` with original
experiment/job/task/fleet/root identities, raw run SHA256 and allowed source
log SHA256 entries. The consumer joins every job to canonical result rows and
checks the original export manifest, campaign summary, and native-log index
bytes under each shard directory. Numeric charges must match canonical job
costs. Native root identity must match the canonical agent and log index; no
child identity is inferred. Missing-agent records may supply no numeric timing.
The original source packet stays local; missing custody refuses telemetry.
First-productive-chunk and total-request p50 use the median; p95 uses nearest
rank, with separate sample coverage. Cake segments are grouped by outcome for
readability; each retains its original selected-task ordinal and tooltip.

Native timing values require a one-time offline producer replay with
`scripts/cloudbench_telemetry.py --membership membership.json --source-root 00=<original-export-root> --output telemetry.json --receipt telemetry-receipt.json --replay-owner <artifact-custodian>`.
Repeat `--source-root` for every recorded shard. The producer verifies full
manifest and original run file hashes, extracts only embedded native events,
joins root/request identities, subtracts original UTC timestamps and leaves
missing or conflicting boundaries null. Selected excerpts alone are not full
source proof. Its receipt binds input manifests/run hashes, producer code,
output bytes, custodian and replay time. Obtain the receipt hash from that
original replay custody handoff; never bless edited telemetry by recomputing
a receipt in the renderer. Rendering checks the pinned receipt and costs
without rereading large original run files every refresh. Captured embedded
logs can be incomplete; timing coverage is per observed request, not all calls.

For all /descend scorecards, publish the interactive HTML embedding only. Do
not send, attach, or display raster images/screenshots. Private DOM inspection
for counts, layout and overflow is permitted; do not emit screenshot output.
