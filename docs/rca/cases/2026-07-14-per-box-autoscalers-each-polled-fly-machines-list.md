## Problem

During 28-wide cloud-benchmark runs the fleet throttled itself: Fly API calls
returned `resource_exhausted`. The traffic was generated by the fleet's own
observers, not by the workload.

## Diagnosis

Each bench got its own autoscaler, and each autoscaler independently ran
`flyctl machines list` once per 10-second interval. With 28 benches that is 28
identical control-plane queries every 10 seconds for state that is global to the
app and identical for every reader. The cost of observing the fleet therefore
scaled O(benches) even though the observed state was O(1). The deeper owned cause
is that read-only pollers were given live API access instead of a shared,
refreshed view.

## Solution

Introduced one controller-level snapshot loop that writes `machines.json` and
`volumes.json` with bounded backoff; every read-only poller consumes the snapshot
instead of calling the API, while only the operations that must see fresh truth
(reaping, pool-claim) stay live (commit 87ddfd3b9). Cemented in
`agents/benchmarks/cloudbench_dependency_sync_test.py`. This is the same class of
defect as the ssh-based status polling fixed the following day — observation cost
growing with fleet size until it starves the fleet's own control operations.

## Human feedback

None recorded.

## Reusable lesson

When N workers each poll the same global state, collapse it into one shared
snapshot loop and let read-only consumers read the snapshot — otherwise the
observers rate-limit the work they are observing.
