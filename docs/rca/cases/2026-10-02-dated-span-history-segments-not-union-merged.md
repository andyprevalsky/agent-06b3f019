## Problem

During `/deploy` run `20261002-191915-1586598`, PR #1341 went `CONFLICTING`
after `main` merged #1354. One of the conflicts was
`agents/benchmarks/history/span_durations.20261002.jsonl`, and it was resolved
by hand as the union of both sides. By the time Group 4 was running, `main` had
appended another 13,015 rows to the same segment (`c4532fbf0`, "record final
deploy history"). Committing this deploy's recorded spans would have made the
PR conflict again.

## Diagnosis

### Evidence

- A temporary commit built off this branch's HEAD (the branch itself was not
  moved) appended one row to `span_durations.20261002.jsonl`.
  `git merge-tree --write-tree` against `origin/main` reported
  `CONFLICT (content)`.
- The same append to `task_attempts.jsonl` merged cleanly. That ledger is
  listed in `.gitattributes` with `merge=union`.
- `git check-attr merge` returned `unspecified` for
  `span_durations.20261002.jsonl` and `span_durations.20261002.02.jsonl`, and
  `union` for the four fixed-name ledgers.

### Root cause

`span_history.py` stops appending to `span_durations.jsonl` once that file
reaches 90 MiB, to stay under GitHub's blob limit. New rows then roll into dated
segments. The primary ledger is now full, so every benchmark run writes to the
current day's segment. `.gitattributes` named only the primary file, so the
segments fell back to a text merge. Two branches that both append rows on the
same day edit the same tail, and git cannot order them.

## Solution

`.gitattributes` now covers `span_durations.*.jsonl` with `merge=union`. The
span-history blackbox case `history_ledgers_union_merged` derives every ledger
name from the recorders: the primary span ledger, two rollover segments
generated by `_append_history_path`, `task_durations.jsonl`, and
`task_attempts.jsonl`. It requires `git check-attr` to report `union` for each
one. It failed before the attribute was added and passes after. The synthetic
merge also became clean.

## Human feedback

None recorded.

## Reusable lesson

When an append-only ledger rolls over into new files, its merge policy has to
follow the rollover naming, not the original filename. Derive the names the
test checks from the writer, so a future naming change cannot silently drop the
merge policy.
