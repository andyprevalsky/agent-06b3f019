AgentCard integration review — 2026-11-08

Current server integration
New company-funded purchase intents use AgentCard's v2 REST Issuing API:
platform client-credentials token, connected user.id, company wallet funding,
explicit single_use cards, Idempotency-Key, structured credential reads, and
exact transfer reconciliation. MCP is retained for optional user tools, legacy
card cleanup and legacy treasury maintenance, rather than new purchase issuance.
The existing AGENTCARD_MINT_ENABLED rollout cutoff remains in force.

Product and financial requirements checked
- Purchase approval, itemized receipt, rejection, secret-ref injection and held
  purchase reuse remain on the existing workflow/UI paths.
- Cards are minted for the approved total, with the provider's 100-cent minimum;
  the request carries the immutable purchase Stripe billing mode and issuance
  refuses a mismatched live/sandbox wallet before creating a card.
- Company funding is checked as an organization setting. Unsupported per-card
  funds_source is not sent. Onramp sandbox creation is excluded because that
  provider path explicitly ignores card idempotency keys.
- Stable purchase/card keys survive pending funding, transport uncertainty and
  retries. Retry-After/retry_after_seconds are minimum waits; the existing
  bounded attempt stops instead of retrying earlier than a long hint.
- A connected provider user is not a legacy cardholder ID. New connections use
  OTP and consent, signed per-user sessions, exclusive credential-scoped bindings
  and hosted KYC; old identities remain available for legacy reconciliation.
- Purchase close requests filter ownership in the database before selecting a
  record, including shared static-card IDs. Another user cannot close/refund it.
- Future minted credential archives allowlist receipt fields. PAN/CVV return to
  the trusted checkout worker but are not persisted by the payment archive writer.
- Financial webhooks require signing configuration; missing configuration fails
  closed. A closed card alone does not substitute for company-funding settlement.
- Exact transfer reads replace newest-100 visibility assumptions on the REST rail.
  Unknown, pending and partial releases are not relabeled as full refunds.

Reproduced reliability/safety defects
The old runtime replayed unkeyed recovery mutations three times after timeouts
and ambiguous unavailable/throttle results. New tests fail on that behavior and
pass with effect-aware retries. Opaque HTTP 429/5xx and Retry-After headers now
use transport status rather than requiring matching prose. Idempotent keyed card
creation retains its safe replay. Runtime timing tests use virtual clocks, removing
real backoff waits and a host-load-sensitive elapsed-time assertion (about 31s to
under 1s for the existing file).
Additional fail/pass regressions cover cross-user close, credential archiving,
missing webhook configuration, billing-mode mismatch, wrong-OTP token refresh,
and provider delay truncation. Binding-race and mode-transition regressions are
also owned by the existing AgentCard store/onboarding suites.

Real provider observations
Read-only platform-token/company-wallet verification passed using sandbox
credentials. An opt-in provider test completed sandbox connection and consent,
100-cent company-funded issuance, same-key same-card replay, simulated clearing,
and automatic card closure. No real purchase or charge occurred.
The real /connect/start response uses id, as its OpenAPI schema specifies; one
narrative guide incorrectly shows connect_id. The implementation follows id and
passes it back as connect_id during verification.
The sandbox labels the charged closed card's closed_reason as canceled rather
than the documented used. This discrepancy remains visible in the test receipt;
financial verification uses the cleared transaction, exact card and amount, and
zero remaining balance, not the closure label.

legitimate already-reclaimed Stripe refund retries retain their behavior.

Another regression proves a prior ambiguous keyed card mint could lose its
funding marker/backing hold after a later billing or mode refusal. Funding retries
