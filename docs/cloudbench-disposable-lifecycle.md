# Ordinary benchmark resource lifetime

Ordinary `scripts/run-bench TASK ...` startup creates task-owned Machines and forked Volumes. Normal completion, failed startup, task failure, and cancellation retire those exact resources. Spindown means destruction, rather than keeping a stopped task fleet and its billable storage. Available task results, exported artifacts, errors, and cleanup receipts remain local/durable; deleting disposable data never turns missing runtime evidence into a successful result.

Creation uses the existing prebuilt image, warm dependency seed, exact task profiles, bootstrap, and capacity admission. Protected warm/base sources, WHM, borrowed production resources, and other owners are not run-owned disposable resources. This change does not resize benchmark disks or change task execution limits, the task catalog, campaign concurrency, or failure thresholds. Cold allocation has a startup cost; the fake-provider regression establishes lifecycle correctness, not preserved production startup latency.

A running task uses its already allocated workspace and dependency overlays. Code synchronization inside that workspace does not allocate a new Volume. A later CLI invocation in the same workspace at a different code revision creates a new temporary fleet after the prior invocation's resource teardown; the owning regression runs two distinct revisions and verifies no ordinary task Machines or Volumes remain after either run. The warm seed remains in both cases.

The lifecycle records both requested and selected boot transport. Newly created resources use the existing normal config/BOOT path. An ambient staged setting is reported and selects that normal path for disposable creation; it does not require existing-Machine admission. Explicit retained reuse continues to support staged transport.

`--reuse-pool-only` explicitly opts into retained, authenticated borrowed IDs and their existing STOP/return contract. A pool miss still refuses creation in that mode. It does not grant permission to destroy borrowed resources. `--keep-clones` remains an explicit debugging retention request; it is not ordinary spindown or evidence of full resource release.

Disposable deletion is scoped by this invocation's durable ownership registry, exact Machine name/ID and forked Volume attribution. Each destructive request has a durable once-only intent; ambiguous mutation is reconciled by exact reads without repeating DELETE. Exact provider-retained terminal deletion has its existing typed status and is not relabeled as absence. A stopped or transitional object alone is not successful disposal. Missing guest/runtime evidence remains missing in the saved cleanup state and failed result; it is not an indefinite storage-retention exemption for these exact disposable resources. An unreadable identity, foreign/borrowed resource, ambiguous ownership, or live unjoined local owner still fails closed.

App-wide emergency maintenance remains separate: `run-bench stop-all` still means STOP, and does not silently delete anything. App-wide old/orphan storage disposal requires its own explicit target classification and authorization.

New disposable Volumes have scheduled backups disabled after exact run ownership and native mount attribution, before BOOT or worker staging. Each Volume has a once-only configuration intent and verified receipt; an ambiguous setting update blocks task dispatch and leaves the exact resource for disposal. Warm/base seed backup policy remains unchanged. Disk size and snapshot retention are preserved; two code-revision lifecycle controls verify no new retained task fleet or automatic backup set.

Deletion intents survive controller exit. Automatic stale reconciliation and exact-owner recovery read the original typed disposable registry and original owner-bound intent before any dispatch. A recorded DELETE is GET-only on successor runs, including a Volume still waiting for detach; a never-issued owned deletion may dispatch once. Legacy registries keep their existing recovery policy and guest/runtime protections.
